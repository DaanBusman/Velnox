# Velnox — Localization Architecture

**Status:** Phase 0 design proposal. Decided: ship **English and Dutch**, with a controlled
vocabulary so a third language is a data change, not a code change.

---

## The one rule

**No user-visible string is ever written in application source.** Not in a React component, not in
a NestJS exception, not in a validation message. Every one of them is a key resolved against a
locale catalogue. This is the only thing that makes adding a language cheap, and it has to hold
from the first commit — retrofitting it later means touching every file.

---

## Three layers

### 1. `packages/i18n/glossary.csv` — controlled vocabulary

One row per domain term, with the agreed translation in every language and a `translate` flag for
names that must never change (`Proxmox VE`, `HEALTH_OK`, `Velnox`, `Tenant`). It is the source of
truth for UI catalogues *and* for the Dutch documentation, so "node" is never "knooppunt" on one
screen and "node" on the next.

Adding German = adding a `de` column and filling it. See
[packages/i18n/README.md](../packages/i18n/README.md).

### 2. `packages/i18n/locales/*.json` — UI message catalogues

Flat-namespaced ICU MessageFormat. ICU because plural and gender rules differ per language and must
not be encoded in TypeScript. `en.json` is the source; every other file is a translation of it.

CI enforces: every key in `en.json` exists in every other locale, no locale has keys `en.json` does
not, and every ICU placeholder set matches across locales. A missing translation is a build
failure, not a silent English fallback in the middle of a Dutch screen.

Frontend: `next-intl` on the App Router, locale resolved from the user's profile preference, then
`Accept-Language`, then `en`.

### 3. API error codes — machine-readable, rendered client-side

The API returns codes and typed parameters, never a prose sentence:

```json
{ "error": { "code": "cluster.quorum_at_risk",
             "params": { "cluster": "prod-a", "available": 2, "required": 3 },
             "requestId": "01J..." } }
```

The frontend renders `errors.cluster.quorum_at_risk` in the active locale. Benefits beyond
translation: error codes are stable enough to assert on in tests, to alert on, and to document.

## What is deliberately **not** translated

| Content | Language | Why |
|---|---|---|
| Audit events | English | Forensic records. A support engineer reading a customer's audit trail must not have to guess the language it was written in, and a translated action name breaks searching and alerting. |
| Job events and logs | English | Same reason, plus they frequently embed verbatim output from Proxmox, `apt` and Ceph, which is English regardless. |
| Application logs | English | Operator/machine consumption. |
| Database enum values | English | They are identifiers. Only their *display* is translated. |
| Verbatim tool output | Untouched | `pve8to9`, `apt`, `ceph -s` output is shown exactly as produced. Translating it would make it wrong. |

The UI labels the sections where this applies, so a Dutch-language user is not surprised by an
English audit trail.

## Documentation

- `docs/*.md` — English, **canonical**.
- `docs/nl/*.md` — Dutch translations.

Where the two disagree, English governs; the Dutch files carry that statement in their header.

**Trade-off, stated plainly:** two documentation sets double the maintenance cost across fifteen
phases, and the realistic failure mode is Dutch documents silently drifting out of date — which is
worse than having none, because a reader cannot tell. Mitigation: each `docs/nl/` file records the
git hash of the English source it was translated from, and a CI check flags a Dutch file whose
English counterpart has changed since. The check warns; it does not block, so English documentation
is never held hostage to a pending translation.

If the Dutch set later proves to be more burden than value, dropping it is a clean removal — the
UI, the glossary and the error codes are unaffected.

## Formatting and locale-sensitive data

- Dates, times, numbers and byte sizes go through `Intl.*` with the active locale — never
  hand-formatted. Timestamps render in the user's timezone; **maintenance windows render and are
  evaluated in the window's own configured timezone**, which is shown explicitly next to the time.
- Sorting uses `Intl.Collator`, so a Dutch user's node list sorts the way they expect.
- The product name comes from `system_settings.product_name`, not from a hardcoded string — so
  rebranding away from "Velnox" is a settings change, and it is interpolated as `{product}` in every
  catalogue that mentions it.
